# Processing and mixer nodes: spec

Status: STEP1 DONE 9b6b9e3 (wire trim core: `Wire::new`, `gain_db`/`invert`, per-wire `Gain`, versions 1..=2). STEP2 DONE (wire trim UI: `Edit::WireGain`/`WireInvert`/`WirePan`/`BalanceCables`, the chip and popover in `app/src/graph.rs`). STEP3 DONE 3cbfa38 (nodes core, buses only: `Node`, `Wire::to`, topological `MixPlan`, node meters, `compile(dev, layout, rate)`; node UI can start against it, see 5 for what `model.rs` must keep). Steps 4 to 6: no code yet. The Devices detail pane is Sources | Output Channels | Monitors with cables between ([DESIGN](DESIGN.md), `app/src/graph.rs`). This spec adds a middle layer between Sources and Output Channels: small mixer strips ("nodes") that sum several cables into one fader, meter and mute, optionally run a few cheap effects, and feed the output channels. The user's own words were "it could be anything: a device summary card, processing nodes or mixer nodes"; the summary card ships separately, this is the bigger reading. Facts below come from reading `crates/sr-core/src/{mixer,config,meters,preset}.rs`, `crates/sr-core/tests/{prop,swap,no_alloc,bench_mix}.rs`, `crates/sr-audio/src/engine.rs` and [LATENCY](LATENCY.md). Cost numbers marked [INFERENCE] are estimates to be measured in step 6 (the effect and bus costs were measured in steps 3 and 4, see LATENCY section 2).

## 1. Goals and non-goals

Goals:
- A route with no node, or with only neutral nodes, sounds and measures exactly as today: bit-identical samples, same delay in every row of [LATENCY](LATENCY.md) section 1.
- Nodes run inside `Mixer::process` (`mixer.rs`), on the IOProc thread that mixes today. No extra thread, ring, resampler or block buffer in the signal path: zero added frames of latency, except the `Delay` effect, which exists to add latency on purpose.
- Real-time safe: no allocation, lock, syscall or page fault on the audio thread. Every buffer is allocated and prefaulted in `MixPlan::compile` (`prefaulted()` does it for `acc` today) and swapped in through the existing mailbox.
- Compute stays a rounding error: at the 16-node cap the nodes add at most 2 % of the callback period at 64 frames (27 us), against 8.0 us for today's whole 64-channel mix ([LATENCY](LATENCY.md) section 2).
- Old configs and presets load unchanged and, while unused, save byte-identically.

Non-goals, and what is not possible:
- No plugin hosting (AU, VST). A plugin brings unbounded latency and unbounded work per block, an out-of-process XPC hop with its own buffering, and third-party code on the audio thread. The effect list is closed: built-in DSP only.
- No look-ahead above 1 ms by default. The limiter has zero look-ahead (soft clip, section 2.5). Any future look-ahead effect must show its added ms and default to 0.
- No convolution, pitch shift, noise reduction, compressors with long look-ahead, FFT effects. Each needs block sizes or latency this router refuses to add.
- No feedback: nodes only feed forward (a cycle is rejected). Nothing reads a node from a Monitor yet (open question 3).
- No automatic delay alignment in v1. The user sets `Delay` by hand; the tap path is 25-37 ms and the direct path 3-11 ms ([LATENCY](LATENCY.md) rows B and C), so the numbers to match are visible in "Measure delay".
- No change to the GPU, Accelerate or SIMD story: the compiled loops are enough ([LATENCY](LATENCY.md) section 3).

## 2. Node model and effect types

A node is a strip: `channels` (1..=8) input rows summed from its incoming wires, an ordered `fx` insert list (0..=4 effects), then a fader (`gain_db`) and a mute. Bus = a node with no effects. Gain, pan and polarity are not nodes: they are properties of a wire (a wire is already a single scalar multiply in `ramp_add`, so they cost nothing). Mono/stereo conversion is wiring plus the `mono` effect.

| Rank | Item | Where | Value for a Loopback-style router | Added cost |
|---|---|---|---|---|
| 1 | Per-wire gain, polarity, pan | `Wire` fields | Fixes fan-in: two mono sources into one output channel add at +6 dB today (the monitor path averages with 1/n, `MonPlan.wires`, but device wires do not); a -6 dB trim per wire fixes it. Pan = two wires with a law. | 0 (folded into the existing tap multiply) |
| 2 | Bus (the node itself) | `VirtualDevice.nodes` | Sum N sources, one fader/meter/mute, then wire to outputs (a "voices" bus, a "music" bus). | one extra hop per node channel, section 3.1 |
| 3 | Mono converter | effect `mono` | Fold L+R for a mono mic or a mono output. | 0.025 us stereo at 256 (measured) |
| 4 | Limiter (zero look-ahead soft clip) | effect `limiter` | The mixer is unbounded on purpose (bit-exact unity, [ARCHITECTURE](ARCHITECTURE.md) "not limited"); a limiter node is the opt-in guard before the HAL hard-clips. | 0.53 us stereo at 256 below the knee, 1.25 us while clipping (measured) |
| 5 | Simple EQ (2-band shelf) | effect `eq` | Voice cleanup, loudness. | 3.0 us stereo at 256, 0.53 us at 64 (measured; the first estimate was 2.3x low) |
| 6 | Delay (sample-accurate) | effect `delay` | Align a direct source to a tapped app. Adds `ms` of latency by design; the UI says so. | 0.056 us stereo at 256, 0.58 us while retiming (measured) |

Common rules for every parameter change: ramp, never step. Linear gains use the mixer's own rule: `slew()` moves at most `max(|cur|,|target|,1)/RAMP_FRAMES` per frame, 480 frames = 10 ms per unit of gain at 48 kHz, partial per block when a block is shorter (`mixer.rs`: `RAMP_FRAMES`, `Gain`). dB parameters slew at 36 dB per 480 frames, frequencies at 10 octaves per 480 frames. A value that is `NaN` is silence for gains (as `Gain::new`) and "neutral" for effect parameters. A neutral effect (0 dB shelves, ceiling at 0 dBFS with no signal above, delay 0, mono off) is skipped entirely once its parameters have settled, so the signal is bit-identical. State that would be stale after a mute is zeroed on the first block after the node unmutes.

### 2.1 Wire trim (`gain_db`, `invert`, pan as a view)
Parameters: `gain_db` in -inf..=+24 (same `check_db` as sources), `invert: bool`. DSP: tap gain becomes `source.cur * app_sys * wire_lin`, with `wire_lin = +-10^(gain_db/20)` (negative for `invert`, so polarity is the sign of the same multiply). A new `Gain` per wire, key = hash(source, src_ch, to, out_ch), inherited across plans exactly like `srcs`. `slew` already handles sign flips (|cur|,|target| both count, so -1 to +1 takes 20 ms). Neutral = 1.0, so the product with `g.cur * s0` is bit-exact. Pan is not stored: the UI writes two wires of one mono channel with constant-power gains `cos(t)` and `sin(t)`, `t = (pan+1) * pi/4` (centre = -3.01 dB each), and reads pan back from a pair. State: none. Cost: 0. Denormals: none (no recursion).

### 2.2 Bus (node with no effects)
Parameters: `channels` 1..=8, `gain_db` (fader, up to +24), `muted`. DSP: zero `rows[node]`, add every incoming tap with `ramp_add` (which `clean()`s NaN/inf and clamps to +-1e30), then the fader `gain_db` and `muted` are applied as the gain of the node's outgoing taps (no extra pass, like a source gain: `ramp_add` skips a settled 0). Meter = row peak times `max(|cur|,|next|)` of the fader. A muted, settled node is not processed at all. State: the row only. Cost: one `fill` + one `ramp_add` per incoming wire + one `peak`: about one tap-chain per node channel, which the 64-channel bench puts at 0.125 us/channel at 64 frames and 0.27 us at 256 (8.0 and 17.0 us over 64 channels). 32 node channels (the cap, 16 stereo buses, `bench_mix`): measured 1.3-1.5 us over the plain 32-channel mix at 64 frames (0.11 % of the 1333 us period), 1.5 us at 128 (0.06 %), 3.0-3.4 us at 256 (0.06 %); the estimate above was 4.0 and 8.5 us, about 2.5x too high because a bus channel's tap-in and tap-out each replace a direct tap rather than add one.

### 2.3 Mono (effect `mono`)
Parameters: none. DSP on each channel pair (0,1), (2,3), ...: `m = 0.5*(l+r); l = r = m` (an odd last channel passes). Averaging, not summing, so a mono-compatible stereo signal keeps its level. State: none. Neutral: effect absent.

### 2.4 Polarity
No effect: use the wire `invert` flag (2.1). A whole-node flip is the UI inverting every incoming wire.

### 2.5 Limiter (effect `limiter`)
Parameters: `ceiling_db` -24..=0 (default -1), `knee_db` 0..=12 (default 6). DSP, memoryless, per sample and channel: `c = 10^(ceiling/20)`, `k = c * 10^(-knee/20)`. If `|x| <= k`, `y = x` (bit-identical below the knee). Else `u = min((|x|-k)/(c-k), 3)`, `y = sign(x) * (k + (c-k) * u(27+u^2)/(27+9u^2))`. The rational term is a vectorisable tanh approximation that is exactly 1 at u = 3, so `|y| <= c` always and the slope is 1 at the knee. Zero look-ahead, zero latency, no state; it is a soft clip, not a brickwall mastering limiter (it adds harmonic distortion above the knee and aliases; no oversampling because that costs latency). The UI shows the largest reduction in dB as a meter tick: `fetch_max` of `1 - |y|/|x|` bits per node, like the peak cells. It is one `fetch_max` per block, taken after the loop. Cost measured: 1.0 ns/sample below the knee (0.53 us stereo at 256), 2.4 ns/sample while clipping (1.25 us). The ceiling and knee glide by linear interpolation of the two linear limits across the block (slewed per block in dB), so a moving ceiling does not step. No special case for `c == k`: knee 0 divides by zero, `min(inf, 3) = 3`, and the sample goes to `c`, a hard clamp (tested).

### 2.6 Simple EQ (effect `eq`)
Parameters: `low_hz` 20..=min(2000, 0.45 fs) (default 120), `low_db` -18..=+18, `high_hz` 1000..=min(20000, 0.45 fs) (default 8000), `high_db` -18..=+18. DSP: two RBJ cookbook shelves (low shelf, high shelf, slope S = 1, so `alpha = sin(w0)/2 * sqrt(2)`, `A = 10^(db/40)`, `w0 = 2 pi f/fs`) in series, coefficients computed in f64 at compile and normalised by `a0`, run in f32 transposed direct form II per channel: `y = b0*x + z1; z1 = b1*x - a1*y + z2; z2 = b2*x - a2*y`. State: `z1,z2` per band per channel. Zipper rule: `low_db`, `high_db`, `low_hz`, `high_hz` are slewed per block as parameters (rule above) and the coefficients are recomputed once per block, only while a parameter is moving (~60 ns per band: sin, cos, powf); there is no per-sample coefficient interpolation. Denormals and blow-up: after every block each `z` is checked (`!z.is_finite()` -> 0, `|z| < 1e-20` -> 0, `|z| >= 1e20` -> 0), one range compare per state, so an inf burst cannot latch NaN, a decaying tail cannot sit in the subnormal range and the echo of a 1e30 burst does not ring on for seconds (added: the mixer clamps samples to 1e30, so a filter memory over 1e20 is a burst, not audio). Measured on the M3 Max: the biquad on subnormal input costs the same as on normal input (0.91 us against 0.91 us stereo at 64 frames), so the sweep is for other targets and for the tail; it changes a state by less than 1e-20, so block splits stay bit-identical for any signal whose filter memory is above that. Inputs are already `clean()`ed by `ramp_add`, so the filter sees finite values. Group delay of an IIR shelf is frequency dependent and well under 1 ms above 200 Hz [INFERENCE]; it is not counted as latency. Cost: the biquad is a serial dependency, measured 2.9 ns/sample/band (the first estimate of 1.3 was low): 2 bands stereo at 256 frames = 3.0 us, at 128 1.3 us, at 64 0.53 us. A band with 0 dB settled is skipped.

### 2.7 Delay (effect `delay`)
Parameters: `ms` 0..=200 (`MAX_DELAY_MS`). DSP: integer-sample delay `d = round(ms * fs / 1000)` on a ring of `ceil(0.2 fs) + MAX_FRAMES` frames per channel, allocated at its maximum so a retime never reallocates and the line can be inherited. Write the block first (up to two `copy_from_slice` chunks at the wrap), then read `x[t-d]` the same way: correct for any `d >= 0`, including `d < block`. Retime: two read heads, the old `d` fading out and the new in over `RAMP_FRAMES` frames (equal-gain linear), so a slider drag does not click or pitch-bend; a target that changes while a fade runs waits for it to finish (at most 10 ms), then fades to the newest. At `d = 0` and no fade the line only records (a memcpy) instead of being skipped, so raising the delay later plays real history, not stale or empty memory; the output is still bit-identical to the input. State: the ring, the two heads, the fade position. Added latency = `ms` exactly; the UI adds it to the route's reported delay. Cost: a memcpy, measured 0.056 us stereo at 256, 10x that while retiming (per-sample blend with two modulo reads). Memory: 54 KB per channel at 48 kHz (170 KB at 192 kHz), `prefaulted`. Cap: at most 8 delay channels per device, so the plan-swap copy (4.1) stays under ~40 us.

## 3. Config schema

Additive, serde `default` everywhere, in the style of `config.rs`:

```json
"nodes": [{"id":"n1","name":"Voices","channels":2,"gain_db":0.0,"muted":false,
           "fx":[{"type":"eq","low_hz":120,"low_db":-3,"high_hz":8000,"high_db":2},{"type":"limiter","ceiling_db":-1}]}],
"wires": [{"source":"s1","src_ch":0,"out_ch":0,"to":"n1","gain_db":-3.0,"invert":false},
          {"source":"n1","src_ch":0,"out_ch":0}]
```
- `VirtualDevice.nodes: Vec<Node>` with `#[serde(default, skip_serializing_if = "Vec::is_empty")]`. `Node { id, name (<= MAX_NAME_CHARS), channels: u16, gain_db: f32, muted: bool, fx: Vec<Fx> }`, `Fx` = `#[serde(tag = "type", rename_all = "snake_case")]` enum like `SourceKind`. Unknown `type` fails the parse (so an old build never half-understands one; see versions).
- `Wire` gains `to: Option<String>` (node id; absent = a device output channel, today's meaning), `gain_db: f32` (skipped at 0) and `invert: bool` (skipped at false). With `to`, `out_ch` is the node's input channel; when `source` names a node, `src_ch` is that node's output channel. This overloads two names to keep every existing wire valid and byte-identical; the cleaner alternative is open question 1.
- Config construction: 34 `Wire {` literals in 17 files became `Wire::new(source, src_ch, out_ch)` (struct update `..Wire::new(..)` where a field is set); no literal is left outside `config.rs`, so later fields (`to`) need no sweep.
- Version rule: `CONFIG_VERSION` becomes 2, and `Config::validate` accepts 1..=2. The writer picks the lowest version that can hold the content (`Config` and `PresetFile` implement `Serialize` by hand and write `written_version()`, not the `version` field, so every writer follows the rule; the field is only what was read): version 1 unless a wire has `gain_db != 0`, `invert`, `to`, or a node exists. Why: serde ignores unknown fields, so a v1 build reading a v2 file would drop nodes and trims, route at unity (+6 dB louder fan-in, effects gone) and then overwrite the file on its next save. With the bump, a v1 build takes `store.rs` `load`'s path (`file_version() > SUPPORTED_VERSION`): defaults, file untouched, `save` refuses. Cost: downgrade shows an empty config until the user upgrades again; the file is never lost. `store.rs` `SUPPORTED_VERSION` becomes 2. Presets: `PRESETS_VERSION` follows the same rule (`preset_store.rs` already ignores and never overwrites a newer file).
- Validate (additions to `Config::validate`, same message style): ids unique across sources and nodes of the device (a wire's `source` must resolve to exactly one); `nodes.len() <= MAX_NODES` (16); `channels` 1..=`MAX_NODE_CH` (8), total node channels <= 32, `fx.len() <= 4`, delay channels <= 8; every effect parameter finite and in range (2.5-2.7); `gain_db` finite and <= `MAX_DB` via `check_db`; a wire `to` names a node and `out_ch < node.channels` (else `out_ch < dev.channels`); a wire `source` that is a node has `src_ch < node.channels`; a wire cannot go from a node back to a source; cycle prevention: Kahn's algorithm over node-to-node wires, a leftover set (including a self wire) is an error naming one node. `MixPlan::compile` never trusts validate: it drops unresolvable wires as it does today and breaks cycles by dropping the back edges of nodes Kahn cannot order, so a hand-built plan cannot hang or panic.
- Presets: `Preset.devices` holds whole `VirtualDevice`s, so nodes and trims ride along with no schema change; `preset::plan` merges with `..p.clone()`, so the preset's nodes replace the device's (a preset without nodes removes them, exactly as its wires replace the old wires). `Config::validate` already runs on the merged result.
- Undo: `Undo` in `app.rs` snapshots the whole `Config` for 6 s ("Removed X. Undo", preset apply), so node removal and preset apply are undoable with no new code beyond a verb. Removing a node splices it out: each (upstream -> node channel k, node channel k -> downstream) pair is rewired directly with the dB gains added, anything else is dropped. Slider and parameter edits are not undoable, same as source volume today.

## 4. Engine plan (`MixPlan`)

### 4.1 Compile, run, swap
- `MixPlan::compile(dev, layout)` becomes `compile(dev, layout, rate)`: EQ coefficients and delay frames need the sample rate. One call site, `refresh_layout` (`engine.rs`, the `v.handle.set_plan(MixPlan::compile(&dev, &lay))` line) plus 3 in `engine/tests.rs`; a nominal-rate change already rebuilds the aggregate and recompiles. `RAMP_FRAMES = 480` stays a frame constant (10 ms only at 48 kHz; existing behaviour, not widened by this work).
- `Tap` becomes `{ src: Src, dst: Dst, gain: Gain-of-source-or-node, wire: Gain, app: Option<usize> }` with `Src = Input(idx) | Node(row)` and `Dst = Vdev(ch) | Node(row)`. Rows of all nodes live in one `node_buf: Vec<f32>` (`rows * MAX_FRAMES`, `prefaulted`). Nodes are numbered in topological order (Kahn, ties by config order); because a tap's source row precedes its destination row, `split_at_mut` gives the read and write slices without copies or unsafe.
- `taps` is sorted by destination stage and indexed by `node_end: Vec<usize>`, so `run` is: for each node in order, `ramp_add` its incoming taps, run its effects in place over its rows, update its meter; then the vdev taps, then the existing device gain, peak, meters and monitors unchanged. A device with no nodes has an empty node list and runs today's loop with one extra branch.
- Meter row index = position in `dev.nodes` (config order), not topo order, so `Meters::take` can name nodes from `dev` alone. `Meters` gains `nodes: Box<[AtomicU32]>` (32 peaks + 16 limiter reductions) next to `inputs`/`outputs`; `MeterReading` gains `nodes: Vec<(String, Vec<f32>)>` beside `sources`, which the app already polls. Cost per node channel: one `peak` (~10 ns at 64 frames).
- Finite bound: `acc_finite` stays valid because every hop re-enters through `clean()` in `ramp_add`; worst per hop is 64 fan-in x 1e30 x 15.85 (source) x 15.85 (wire) x ~10 (shelf boost) x 15.85 (fader) = 2.5e36 < f32::MAX, rechecked in the test plan. `MAX_FINITE_TAPS` is recomputed with node fan-in.
- `clipped_blocks` keeps its definition: a block where a virtual-device output sample had `|x| > 1.0` (counted at the device stage in `run`, unchanged). A limiter node only bounds its own bus, so a sum of several buses can still count; the node meter shows its own peak above 1.0 in `bad`.
- Swap and crossfade: `route` hashes `(in, vch, source key)` per tap and the monitor wires today; it adds, per node, `(id, channels, fx kinds in order)` and the node-level wires, and still excludes every gain and effect parameter. Parameter edits (fader, EQ, delay ms) therefore ramp inside one plan with no crossfade; structural edits (node or effect added or removed, wire re-pointed) differ in `route` and take today's path in `Mixer::poll`: the old plan runs one more block into `fade_buf` and `crossfade()` blends linearly over that block (1.3 ms at 64 frames). `MixPlan::inherit` also continues node state: same node id and same effect kind at the same position keep their `z1,z2`, delay ring and heads. When `route` is equal the old plan is discarded, so `inherit(&mut self, old: &mut MixPlan)` swaps the state `Vec`s (pointer swap, O(1), no allocation). When `route` differs the old plan still has to run the crossfade block with its own state, so only the small biquad state and the delay rings are `copy_from_slice`d (<= 8 delay channels = 430 KB at 48 kHz, ~30 us once, from a swap that already costs a block of mixing twice). A new delay or EQ starts cold: inserting `delay` creates a gap of `ms` by definition; a new neutral EQ is identity. `in_len`/`out_len` equality still gates the crossfade.
- Engine side: `layout_inputs` reads `dev.sources`, never `dev.wires`, so a Device source wired only through a node is already read and it needs no change (the first draft of this spec said otherwise). `without_feedback` does scan wires: its direct test (`w.out_ch == mw.out_ch && w.src_ch == mw.dst_ch`) would read a wire into a node's input channel as a wire onto the vdev channel of the same number, so it is now `reaches_vdev`, a walk over node rows that finds the loop through any chain of nodes and ignores wires that only feed a node. `plan_only_change` needs no change: nodes and wire edits are plan swaps. `layout::build_layout` is unchanged: nodes need no aggregate channel. `publish_plan` passes the main device's nominal rate (48 kHz until the HAL reported one).

## 5. UI plan

Constraint: at the 1000 px minimum window the graph pane is 750 px wide (sidebar 250, `SIDEBAR_W`), cards are 191 px (`Layout::compute`) and the gutters between columns are 64 px. A fourth column does not fit (4 x 180 + gaps > 750).
- Nodes are slim vertical strips (84 px: title, meter ladder of the 20-segment style, fader, mute, effect chips) placed in the gutter between Sources and Output Channels. While a device has nodes, `Layout::compute` clamps `card_w` to 150..=250 and sets the gutter to 124 px: 3 x 150 + 2 x 124 + 48 = 746 <= 750, so it still fits at the minimum; a wider window keeps the present proportions. Several nodes stack vertically with `GAP` and scroll with the graph. Step 5 must view snapshots at 1000 px dark and light before merge.
- Model: `CardId::Node(usize)`, `Port::NodeIn { node, ch }` / `NodeOut { node, ch }`, `can_link` allows Src->NodeIn, NodeOut->NodeIn (later node), NodeOut->OutIn and Src->OutIn; `links()` reads `to`/node sources; `feeding_source()` follows nodes so a cable takes the colour of the first upstream source (grey when none), as today's output-channel rule. New `Edit`s (the graph only emits edits, `model::apply` mutates): `AddNode`, `RemoveNode`, `NodeVolume`, `NodeMute`, `NodeFx(add/remove/move/param)`, `WireGain`, `WireInvert`. `Port::OutIn` `Disconnect` (`model.rs` `dev.wires.retain(|w| w.out_ch != ch)`) must also require `w.to.is_none()`, and the channel shrink retain must keep node wires.
- Adding a node, three paths, all keyboard reachable: (1) hover a cable: next to today's x (`wires_and_ports`, the `painter.circle(mid, 9.0, ...)` affordance) a `+` circle appears, 28 px hit area; click inserts a node on that cable (one wire in, one wire out, channel for channel). (2) A source card's options row gets "Add mixer", which routes the source's wires through a new node. (3) The Output Channels header menu gets "Add mixer" for an empty node you wire by hand. Names: the node is "Mixer" in the UI (sentence case, as [DESIGN](DESIGN.md) Copy), effects are "Mono", "EQ", "Limiter", "Delay".
- Inspector: the strip's title button opens a popover (the `source_popup` pattern: `Popup`, `PopupCloseBehavior`): name, "Add effect" menu, per-effect parameter sliders (each with a text field and a `WidgetInfo` label such as "Low shelf gain, dB"), up and down buttons to reorder, remove. Delay shows "Adds 12 ms". Wire trim: clicking a cable's middle opens a small popover with Gain (dB), "Flip polarity", and Pan when the wire belongs to a mono L/R pair; the x stays the one way to unplug.
- Keyboard: strips and jacks are in the tab order (`name_button` gives each jack its accessible label today); Space or Enter opens the inspector, arrow keys move sliders, Esc closes; the 2 px `focus` ring from [DESIGN](DESIGN.md) applies; the `+` on a cable has an equivalent "Insert mixer on this cable" action in the inspector of either endpoint. No colour-only state: muted shows the switch state in text for screen readers.
- Tokens only (`theme.rs`): strip = `raised` card with `hairline`, radius 14; fader knob `slider_knob`; meter = existing `meter` widget; no new colours, no shadow. An idle window still requests no repaint (the existing test must still pass).

## 6. Test plan and implementation sequence

Tests (all against the existing harnesses):
- Oracle properties (`crates/sr-core/tests/prop.rs` style, a naive f64 reference of buses, wire gains, biquads, soft clip, delay): random DAGs of up to 6 nodes, constant and sine inputs, tolerance of the existing gain oracle for gain-only graphs and 1e-4 relative with EQ (f32 state vs f64). Delay: an impulse arrives exactly `d` samples later for `d` in {0, 1, n-1, n, n+1, 4800} and for block splits {1, 64, 256, 4096}.
- Neutral is bit-exact: a graph with a node that has no effects, 0 dB wires and a 0 dB fader equals the direct-wired mixer under `f32::to_bits`, for single and multiple sources per channel (same tap order). Same for each effect while neutral (limiter below its knee, delay 0, EQ 0 dB, mono absent).
- Block-size invariance: after parameters settle, output of a node graph processed in different block splits is identical (stateless effects) or bit-identical for biquad and delay (state continuous).
- Swaps (`swap.rs`): extend `Cfg` with a node, random add/remove/retime/reorder between blocks; assert no sample step above the existing `reach` bound extended by node faders, no NaN, and that a delay retime does not click. Fuzz seeds like `store.rs` proptests.
- RT: `no_alloc.rs` runs `process` and a plan swap with every effect present; `rt_faults.rs` is the page-fault test (it gains a plan with 32 node channels), so the NaN, inf and 1e38 bursts through every effect live in `nodes.rs` and assert output finite and recovery within one block. The node plan in `rt_faults.rs` found a fault that was already there: the first crossfade touched `fade_buf` (1 MB, zero pages) on the audio thread; `mixer()` now prefaults it.
- Config: golden serialization of `EXAMPLE` and of a current `config.json`/`presets.json` fixture unchanged; v2 round trip; a v1-labelled file with nodes still loads; cycle, self wire, duplicate id, over cap and bad range cases; `prop.rs` `arb_device` extended so `validate().is_ok()` implies `compile` never panics and `process` stays finite.
- Perf: a `bench_mix.rs` scenario (16 stereo nodes with all effects, 64/128/256 frames), results added to [LATENCY](LATENCY.md) section 2; the 2 % at 64 frames gate (27 us) is a review gate, not a CI assertion (timing flakes).

## 7. Risks and open questions

Risks: (a) the downgrade refusal (v1 build shows defaults) surprises a user who rolls back; mitigated by never touching the file. (b) A structural edit crossfades over one block, 1.3 ms at 64 frames, so a very short click remains possible when adding an effect that changes level; the existing wire add/remove accepts the same. (c) The soft clip is not a mastering limiter; the UI must not call it one. (d) Delay changes the route latency; if a user sets 200 ms on a mic, "Measure delay" must show it or the feature looks like a bug. (e) Memory per plan grows by up to ~1 MB (rows 512 KB, delay 430 KB at 48 kHz) and a crossfade keeps two plans alive. (f) The engine owner is changing `engine.rs` apply paths concurrently; step 3 needs a merge window. (g) Every effect cost and the denormal behaviour are now measured (LATENCY section 2); the group delay of the shelves [INFERENCE] is not.

Open questions:
1. Keep `Wire` overloaded (`to`, node `source`) for byte compatibility, or add a `routes` list at version 2 and migrate wires on first save? The overload is smaller; the list is cleaner but breaks the "v1 content saves as v1" rule.
2. Store pan as a field instead of a derived view of two wire gains? A field is easier to read back, but doubles the model for one UI control.
3. Should a Monitor tap a node (per-headphone EQ)? It needs a second node set after the device gain and a second schedule; not in v1.
4. Limiter look-ahead: allow 0..=1 ms as an explicit, displayed latency, or keep it out for good?
5. Should "Measure delay" suggest the `Delay` value that aligns a direct source to a tapped one (from the engine-reported 25-37 ms vs 3-11 ms)?
6. Node-level colour: a bus mixing several sources has no single cable colour; first-source rule (above) or a neutral `ink`?
